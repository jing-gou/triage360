## Problem Statement

我同时在 GitHub、Gitee、Jira、飞书上被指派任务。每个平台只让我看到它自己那一份「指派给我」，没有任何一处能回答**今天到底该做什么**。

每天早上我要逐个打开四个视图、在脑子里把「同一件事在不同平台上的两条记录」认出来是同一件、再判断优先级。真正的成本不是看不到，而是**合并与判断**，以及随之而来的漏看——漏掉的那一条往往是线上问题。

国内场景还多一层硬约束：Gitee 官方 API **没有跨仓库「指派给我」端点**（已核实其 scope 枚举与 API 列表），所以任何面向国内开发者的聚合都必须自己拼装。

## Solution

一个多租户 Web 面板：连接我的账号后，按 provider 拉取派给我的 issue（**只读，绝不回写**），归一化成统一形状，把指向同一件事的跨平台条目**合并成一张卡**，再用规则打分产出「今日清单」，我用拖拽调整顺序。

两个 AI 出口分别承担不同延迟预算：**「为什么是这几条」**给单条排序理由（同步、2 秒内），**「AI 提炼」**给批量任务摘要（按钮触发、流式逐条、允许回答「信息不足」）。我第一次主动排序后，系统开始学习我把哪一类任务排在前面。

首次访客不需要连接任何账号：打开即是**代持演示租户**的真实数据，含跨平台重复项与私有仓库条目。

## User Stories

### 接入与登录

1. As a 首次到访的访客, I want 打开链接就直接看到一张填好的今日清单, so that 我不用为了判断这个工具值不值得用而先做一次授权决策
2. As a 开发者, I want 用 GitHub OAuth 登录且登录本身就是第一个 provider 连接, so that 我不需要注册第二个账号体系
3. As a 只愿意暴露公开仓库的开发者, I want 选择「只读公开仓库」这一档授权, so that 我不必为了试一个工具就把私有仓库整体交出去
4. As a 在私有仓库工作的开发者, I want 单独再授权「包含私有仓库」这一档, so that 我的真实工作负载能出现在面板里
5. As a 已授权的用户, I want 看到系统**实际**被授予了哪些 scope（而不是我以为它有的）, so that 我知道面板少显示的东西是我在 GitHub 侧改了权限造成的
6. As a Gitee 用户, I want 用 Gitee 账号连接, so that 国内仓库的指派也能进同一张清单
7. As a Jira 用户, I want 在界面上看到 Jira 卡片被诚实标注为「样例数据」, so that 我不会误以为已经接上了我自己的站点
8. As a 飞书用户, I want 看到飞书卡片并读到「真实接入需企业自建应用」这句话, so that 我知道路线图的位置而不是以为它坏了
9. As a 想退出的人, I want 一键断开某个平台, so that 我不必去三个平台后台分别找这个应用

### 凭据与安全

10. As a 授权用户, I want 在点「连接」之前先看到一张「我们存什么 / 不存什么 / 谁可见 / 怎么清」的表并显式同意, so that 我知道自己在交出什么
11. As a 授权用户, I want 撤销授权后我的 token 与全部数据被物理删除, so that 「撤销」不是一个假动作
12. As a 长期不来的用户, I want 系统在 30 天未访问后自动清除我的数据, so that 我不会在忘记已久的服务器上留下悬空凭据
13. As a 关心泄露后果的用户, I want 知道 token 是加密落库、且这个加密**挡不住服务器被完全控制**, so that 我能按真实风险判断而不是被一句「我们会保护您」打发
14. As a 维护者, I want issue 正文、评论、diff、代码永远不入库, so that 拖库与备份外泄的伤害上限被限制在元数据与标题
15. As a 维护者, I want 日志里永不出现 token、授权头和用户正文, so that 一次误配置不会把凭据写进可被读取的日志文件
16. As a 审查代码的人, I want 在代码里看到一个明确的 provider `scopeDescriptor` 而不是散落的 if, so that 各平台授权粒度不对称这件事被记录在结构里

### 今日清单与规划

17. As a 每天早上只有 60 秒的人, I want 首屏直接是「今天该做的 N 条」而不是全量列表, so that 我不需要自己再做一次筛选
18. As a 用户, I want 同一件事在 GitHub 与 Gitee 各有记录时被合并成一张卡, so that 我不会重复处理同一个问题，也看不到它其实被派了两次
19. As a 用户, I want 在合并卡上看到它来自哪几个平台并分别跳转, so that 我仍能回到原始出处处理
20. As a 用户, I want 拖拽调整今日清单顺序, so that 机器判断和我当日的实际情况冲突时我有一票
21. As a 用户, I want 已完成的条目自动从今日清单收敛掉, so that 清单长度只反映真实未完成工作
22. As a 用户, I want 源站已删除的条目在下一轮后消失, so that 面板不会长期挂着一条已经不存在的任务
23. As a 用户, I want 逾期项与今日到期项在视觉上强于普通项, so that 时间压力不需要我读标题就能感知
24. As a 用户, I want 点击条目跳到源站处理, so that 这个工具不需要承担「在面板里完成工作」的职责
25. As a 用户, I want 手动 refresh 并看到本轮拉取了哪些 provider, so that 我不必怀疑自己看的是不是最新数据
26. As a 用户, I want 面板在标签页不可见时停止轮询, so that 我的后台额度不会被一个开着的旧标签页吃光

### AI

27. As a 用户, I want 规则打分决定顺序、LLM 只负责把理由说成人话, so that 排序是可解释的而不是模型的直觉
28. As a 用户, I want 点「为什么是这几条」在 2 秒内拿到单条理由, so that 这个交互不会退化成等转圈
29. As a 用户, I want 点「AI 提炼」后卡片一条条被填上任务摘要, so that 我可以边看它生成长边拖拽排序
30. As a 用户, I want 摘要只基于标题与标签并明确告诉我这一点, so that 我不会把它的推断当成读过我代码的结论
31. As a 用户, I want AI 被允许回答「信息不足」, so that 它在看不懂的条目上不会编造
32. As a 用户, I want 摘要按「条目 + 更新时间」缓存, so that 没变化的条目不会每次重新付费重等新结果
33. As a 首次手动排序的用户, I want 一个弹窗告诉我它现在学的是什么, so that 「学习机制」不是一个营销词
34. As a 老用户, I want 理由里出现「因为你连续把 X 仓库排在前面」这类引用, so that 我能确认学习真的生效了
35. As a 用户, I want 排序行为被记录、被清除、被 30 天过期覆盖, so that 偏好数据和我其余数据同命

### 演示租户

36. As a 首次到访的访客, I want 默认看到的演示账号是真实连接、真实拉取、会随时间变化的, so that 我不会把它当成静态原型
37. As a 首次到访的访客, I want 默认只有精选 12 条, so that 我在 60 秒内看得完并理解价值
38. As a 首次到访的访客, I want 一个「展开完整视图（83 条）」的开关, so that 我能亲眼看到它在信息过载时仍然只推那三条
39. As a 首次到访的访客, I want 演示数据里包含私有仓库条目, so that 公私授权这一档差异能被演示出来
40. As a 首次到访的访客, I want 演示数据里包含一条标题信息量极低的条目, so that「AI 会说不知道」这件事被展示而不是被声称
41. As a 维护者, I want 演示租户被定时刷新并带并发锁, so that 它不会因为 24 小时无人访问就变空
42. As a 维护者, I want 重置演示态的入口, so that 一次误操作不会毁掉整个 demo

### 状态与失败

43. As a 用户, I want provider 状态收在右下角一个安静的角标里, so that 健康状态不占用我的注意力
44. As a 用户, I want 某源拉取失败时受影响的那几条卡片就地标注「来自 12:07 快照」, so that 我不用理解任何全局状态就知道哪些数据可能旧
45. As a 用户, I want 授权过期显示为「重新连接」而不是一片空列表, so that 我能区分「今天真没事」和「凭据失效了」
46. As a 用户, I want scope 不足导致的失败被解释成「权限未授予」, so that 我不会把它误读成服务故障

### 维护与交付

47. As a 维护者, I want 三条固定的 OAuth 回调路径且不开 wildcard, so that 三家的回调登记不会因为地址可改而失效
48. As a 维护者, I want 前端托管在 Qoder Sites 且设为公开访问, so that 任何链接持有者点开即用，不需要注册或先配置任何东西
49. As a 维护者, I want 新增一个 provider 只需要实现统一契约的七个方法, so that「已给飞书留好位置」这句话是可验证的
50. As a 未来的我, I want 这份 spec 与 DECISIONS.md 互相引用, so that 两周后我还能知道某个决定当初为什么这样定

## Implementation Decisions

### 架构与接缝

- **前端托管 Qoder Sites（公开访问）+ 后端在自有服务器**（已有域名与 HTTPS）。理由三条且都是一手事实：换取 token 必须服务端（GitHub/Gitee 的 `client_secret` 均 Required、PKCE 不替代、Atlassian 无 implicit flow）；Gitee access_token **一天过期**需要真定时器；回调 URL 需在三家后台预登记、要永久稳定的主机名。
- 回调三条固定路径 `/cb/github`、`/cb/gitee`、`/cb/jira`，**不开 wildcard**。
- 站点密钥使用 Qoder Sites 的服务端 secret 存储（平台声明读取接口永不返回明文），`client_secret` 不进前端包、不进仓库。
- **Provider 统一契约（内部，不开放第三方插件）**：`search()`、`getByIds()`、`normalize()`、`doneStates`、`deletedStates`、`pollIntervalMs`、`scopeDescriptor`。界面与规划层只认归一化后的形状。`scopeDescriptor` 必需，因为各平台授权粒度不对称。`normalize()` 在阶段 1 定稿，否则跨平台合并会建在各家原始字段上。
- 批量刷新语义借自 Super Productivity：按 id 批量取回（未返回的 id 视为「跳过」而非「已删除」），并把已存在 id 集合传给 provider 以实现 backlog 自动导入。**每 provider 每轮 ≈ 一个批量请求**，不是每任务一个。

### 四个 provider 的真实程度（必须各自标明，不得含糊）

| Provider | v1 形态 | 决定性事实 |
|---|---|---|
| GitHub | 真连、对外，双档授权 `public_repo` / `repo` | `api.github.com` 实测 `Access-Control-Allow-Origin: *`，且 `Access-Control-Expose-Headers` 暴露 `X-OAuth-Scopes`，前端可直连并读到实际 scope |
| Gitee | 真连、对外 | 有独立 `issues` scope；access_token 有效期一天；官方无量化限流；换取 token 需 `client_secret`；403 常见原因是缺 `User-Agent` |
| Jira | 真连但**仅内部自证**，app 保持默认 private、不开 sharing，UI 一律标「样例数据」 | Atlassian 规定 app 只能访问**已安装它的站点**、consent 屏要求用户选站点，且未审核应用会向用户显示警告页 |
| 飞书 | 第四张样例卡，零真连代码 | 自建应用仅限本租户，外部用户必然连接失败 |

- 跨平台表述口径统一为「统一抽象层 + N 个适配器」，**不**表述为「已接通的平台数量」。
- 「已跑通真实 3LO 接入（截图为证）」这句话只能出现在阶段 5 完成之后；无证据即从对外文案里删除。

### 凭据与数据

- 服务端代持：token **AES-256-GCM** 加密落库，密钥同机。对外措辞精确到「数据库文件泄露不导致凭据泄露」，并**明写挡不住服务器被完全控制**（对齐 Super Productivity 自己公开写明 `unencrypted at rest … an isolation boundary` 的做法）。
- 镜像：**元数据全量 + 标题入库；正文、评论、diff、代码永不入库**。打码属于展示层策略，与「标题是否入库」是两件事，不得混淆。
- 刷新分档：演示租户 cron 定时 + 分布式锁；真实租户懒刷新（访问时判 `expires_at`）；过期态显式可见并给「重新连接」。Atlassian 轮换 refresh token 必须**原子替换**——用坏一次永久丢一个租户。
- 撤销 = 物理删除该租户 token 与全部数据；30 天未访问自动清除；**不做数据导出**。撤销为**一键全撤**，另附一句文案引导需要精细控制的用户去 GitHub 调整 scope。
- 日志纪律：永不记录 token、授权头、含用户正文的响应体；错误上报前对 URL 打码（URL 可能携带 token）。
- **不做节流**（有意承担的风险，见 Further Notes）。

### AI

- 规则打分决定顺序，LLM 只做措辞，输入仅元数据。
- 两个功能分别命名、分别计时：**「为什么是这几条」**同步返回、2 秒硬指标；**「AI 提炼」**按钮触发、一次 ≤20 条、缓存键 `provider + issue_id + updated_at`、并发流式逐条填充、允许输出「信息不足」。
- 界面明示「AI 只看得到标题和标签，看不到正文和评论」——主动示弱换可信度。
- 运行位置：自有服务器 + 自有模型 key。Qoder Cloud Agents 仅作为 30 分钟验证支线（能否被非 Sites 后端调用无文档）。
- **学习闭环做最小可实现版**：记录 `provider + issue_id + 时间 + 位置`，按 repo/label 历史命中线性加权；首次主动排序后弹窗说明学的是什么；理由文案可引用它。若未通，唯一允许的降级是文案改为「只记录、闭环在路线图」。

### 演示与界面

- 新注册**专用演示账号**（不用真实工作账号），必须含 ≥1 私有仓库。83 条对照数据必须在源站真实存在，不得前端伪造。
- 双层数据集：默认精选 12 条（1 逾期 / 2 今日到期 / **2 条跨平台重复项，措辞相似但不同** / 1 私有 / 1 低信息量 / 2 已完成 / 3 一般），可展开 83 条对照视图。
- 界面常态安静：状态收在右下角角标，异常才变色；失败时把「来自 12:07 快照」**就地打在受影响卡片**，不做顶部横幅、不做常驻状态卡。

## Testing Decisions

只测外部行为，不测实现细节。**两条 seams**，覆盖价值最高且最容易静默坏掉的两处：

1. **今日清单构建器**（顶层 seam，约 90% 价值）：注入时钟 + 注入 provider 的假 HTTP（形状即可替换的 `PluginHttp` 那类适配器），输入一批 provider fixture，断言输出的有序清单、合并结果、每条的理由来源。被这个 seam 覆盖的行为包括：`normalize()`、`doneStates`/`deletedStates` 收敛、跨平台重复项合并、规则打分、学习加权、按 id 批量取回、分页（通过 fixture 表达）。**不**为这些模块单独写单元测试——它们只在清单构建结果里对用户可见。
2. **凭据生命周期决策器**：输入 `(now, expires_at, last_refresh_at, is_demo_tenant)`，输出动作 `serve | lazy-refresh | scheduled-refresh | expire-to-reauth`；并断言轮换 token 的替换是原子的（新值落库前不得让旧 refresh token 进入失效处理路径）。这一条单列的理由很具体：Gitee 一天过期与 Atlassian 轮换失效都会**静默**让用户看到空面板，属于最难当场发现的一类故障。

**不写自动化测试的部分**（走手工验收清单 + 截图，这是两周预算下有意做的取舍）：加密与解密路径、OAuth 回调 handler 的 HTTP 细节、拖拽交互与视觉、AI 摘要文案质量。它们的失败是**可见的**，与上面两类的静默失败性质不同。

判断「测试写得好」的标准：只断言这两条 seams 的输入输出，不 peek provider 内部结构、不断言 SQL 形态、不断言 prompt 文本。prior art：本仓库尚无代码，seam 1 的 fixture 可直接借 Super Productivity 的 provider 返回形状（见 `research/super-productivity-implementation.md` §3）。

## Out of Scope

- 向任何外部平台**回写**（改状态、加评论、建任务、时间块、工时）
- 数据导出、跨设备同步协议、离线模式
- 独立账号体系（登录即 GitHub 连接）
- 第三方插件式 provider 加载（zip 上传、运行隔离、保留 id 反冒充那一整套）
- Gitee / Jira / 飞书的公开-私有授权粒度开关（平台上不存在该粒度，做出来会是假开关）
- Jira 与飞书的对外真实接入（Jira 仅内部自证；飞书仅样例卡）
- Atlassian Marketplace 上架与第三方集成审核
- 推送通知、webhook、后台常驻任务（除演示租户的定时刷新）
- 上游请求节流与配额预算（Q31 有意不做）
- 移动端与响应式适配
- 任何超出「记录排序 → 线性加权」的偏好建模，以及任何超出已实现范围的能力声称

## Further Notes

- 线上可访问地址是唯一的体验入口，介绍文字只是入口。链接接收方不会先读文档就会点进来真用，所以**线上真实体验决定它是否被理解**，不接受「介绍写得清楚但产品打不开」。
- 五步上手路径：打开（默认演示租户）→ 看今日清单 → 拖拽排序（首次触发学习说明）→ 点「为什么是这几条」看 2 秒理由 → 连接自己的账号并自选 public/private。任何进不了这五步的能力，在首次上手时等于不存在。
- 自述文档里应当包含**被推翻的判断**（例如 Atlassian Global Pool 初读错误、「介绍文字优先」假设被推翻），并附上每条 claim 的一手出处；这类「我如何发现自己错了」的记录是唯一无法事后编造的过程凭证。
- 四项仍未文档化、会在阶段 1/3 咬人的事实，以及各自的自证配方，记录在 `DECISIONS.md` §3 末表；其中「Gitee 限流是否按 IP 计」与「不做节流」直接相乘，是最可能当众发生的故障。
- **对外演示脚本被显式推迟**到核心场景稳定之后，不是遗漏。届时需要重新决定的两件事：现场断网兜底录屏，以及被质疑数据造假时是否当场真连。

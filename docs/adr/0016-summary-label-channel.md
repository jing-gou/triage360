# ADR-0016 · 摘要的标签通道与「AI 提炼」的边界：labels 挂在清单条目上，不进任务八键

**决策**：「AI 提炼」（#20）的上行输入只有**标题 + 标签**。标签由 provider 自己从源站原件里读（`Provider.labels(raw)`；provider 契约因此从七法扩到八法，ADR-0002 已留后记），随后挂在**清单条目**（`ListEntry.labels`）而不是任务上：T03 定稿的八键（`id` / `providerId` / `title` / `url` / `state` / `updatedAt` / `dueAt` / `duePrecision`）保持不变，标签不参与归一、打分、合并与跨轮快照。合并卡的标签取各来源的并集——一张卡代表同一件事的全部来源，只取表头的标签会把另一侧的信息丢掉。摘要走服务端单条通道 `POST /api/summary`（Bearer 会话标识，必须有租户），面板一次最多取前 20 张卡并发 3 条调用，哪条先回来先填哪张；缓存键是 `provider + issue_id + updated_at`，落在浏览器 localStorage，源站未更新不重算。模型允许且被要求在标题与标签不足时只输出「信息不足」。演示屏没有会话，摘要由服务端在刷新演示快照时预生成（键为 `<html_url>@<updatedAt ISO>`），按同一个键缓存、只补缺失的，按钮只负责展开——公开演示屏因此不会触发访客侧模型调用。

**原因**：PRD US#30 与 `DECISIONS.md` §0.5 都要求摘要「只基于标题与标签」，但标签从来没进过数据通道，这句话此前没有数据来源。把标签塞进 `Task` 会动 T03 的定稿形状，连带跨轮快照、形状门与所有 provider 的 normalize；它只是措辞的输入，不进比较层，放条目上是更窄的改动。缓存放本机而不是账本：摘要不是凭据，写进服务端账本只会扩大「撤销即物理删除」的删除义务与加密边界，换来的收益（跨浏览器共享）在演示规模下不值。演示预生成是为了守住「首访无会话也能看到 AI」的同时不把模型钥匙变成公开端点：刷新这一侧本来就有定时器与并发锁，按 `updated_at` 缓存后重复成本接近零。

**被放弃的选项**：把标签加进 `Task` 第九键（动定稿形状与全部 provider，学习加权也还没定这条通道）；摘要要求访客先连接（首访演示屏看不到 AI，五步路径少一环）；开一个公开摘要端点（没有会话闸门，等于把模型配额挂在公网）；把摘要写进演示快照以外的账本或服务端缓存（扩大删除义务）；一次批量 SSE 流（服务端复杂度上升，逐条 POST 已经能满足「边长边拖」）；对摘要做硬截断或自动质量断言（与 ADR-0013 同一个理由，质量走人工判断）。

**已知缺口，刻意留着**：合并卡按表头记录的 `provider + issue_id + updated_at` 缓存、标签取并集，兄弟来源单独更新不会让这张卡的摘要失效；跨轮失败家的条目没有原件，标签为空，摘要更容易被判「信息不足」；演示预生成按最近更新的 20 条取，数据涨到 83 条时低信息量条目必须排进最近一档才会被覆盖；`parseSummaryCard` 对超限输入整卡拒绝，面板只给一句「N 张卡没有提炼出来」。摘要只在真实会话与演示快照上出现，样例屏没有输入也没有预算；Gitee 的标签形状若与 GitHub 不同，由 provider 的 `labels()` 各自消化，核心层不认平台；演示预生成只覆盖未完成的 20 条，其余条目要等下拉后的刷新；`/api/summary` 与 `/api/reason` 一样没有按租户限流（演示规模，先不加）；标签通道的最终归属（是否进 `Task`、学习加权怎么用）仍由 #36 决定，这份 ADR 只覆盖摘要这一处消费。

# ADR-0005 · 打分档位由构建器算，"今日" 取访客的日历日

**决策**：顺序由 `buildTodayList` 里的 `ruleOf(task, instant, zoneOffsetMinutes?)` 决定，返回值是三档之一的**理由标识** `reason`（类型 `RuleId`）：`overdue`（`dueAt < instant`）→ `dueToday`（`dueAt` 与 `instant` 落在访客的同一个日历日）→ `noDeadline`（没有 `dueAt`）与 `dueLater`（截止在更晚的那天）；后两个共用一档。档位先后写在 `RANK: Record<RuleId, number>` 这一张表里，规则本身不出现数字。档内先按 `updatedAt` 倒序，再按 `id` 的码位序破平。理由跟着**清单条目** `{ task, reason }` 出来，不进 `Task`：定稿的七键不因打分而变第八键。界面只把标识翻译成词（`REASON_LABELS`），不重算档位；US#23 要的那种「强于普通项」由卡片自己的左边框承担（`styles.css` 的 `.card--overdue` / `.card--dueToday`），不靠把每张卡的理由都加粗。

日界由**注入**的 `zoneOffsetMinutes` 决定：省略即 UTC 日，界面每次构建传 `-new Date().getTimezoneOffset()`。只写日期不带时刻的原始截止值一律折算成当日 23:59，折算只发生在 `toDueInstant` 一处。

**原因**：US#27 要的是「规则打分决定顺序、LLM 只负责把理由说成人话」，而置顶的依据是「今天不做就来不及」，不是「刚有人动过」——测试里刻意让逾期项三天没动、干扰项两小时半前才动，按 `updatedAt` 排必然反。分档而不是加权：v1 只有三条规则，一个分数会把 #8「为什么是这几条」需要的可解释性换成一个没人能读的数字，而 #10 学习加权真要加分时 `RANK` 这张表就是它的落点。破平必须靠 `id` 而不是数组位置：provider 返回的顺序不属于本应用，T05 合并四家之后更挡不住——AC#4 那句「同一输入的两次运行一致」只有在这种反例上才可能失败，否则它是一条永远绿的断言。比较用码位序不用 `localeCompare`：id 里带 `:` `#` `/` 与大小写，ICU 给的顺序随宿主变，而今天这批 ASCII 样本还测不出它变了。

**第三档为什么要两个标识**：票面 AC#1 给这一档的词是「其他」。它是个 catch-all——没有截止和截止在十天后进的是同一档，但「最近更新」对后者是句假话，而 AC#2 要的恰恰是原因本身。所以档位不变（`RANK` 里两者同为 2）、标识分开，界面翻译成「无截止时间」与「未到截止日」。

**"今日" 为什么从 UTC 日界改成访客日历日**：本 ADR 第一版把代价写反了，写的是「副作用出现在本地 00:00–08:00：一条今天 UTC 23:59 截止的任务会被说成今日到期，而按本地它已是明天早上」。实测（`TZ=Asia/Shanghai node` 复算 `ruleOf`）：UTC+8 下 `utcDay(dueAt) === utcDay(instant)` 覆盖的本地窗口是本地 D 日 08:00 → D+1 日 07:59，于是

- **本地 00:00–07:59：「今日到期」这一档基本是空的。** 当天中午截止的条目属于下一个 UTC 日，落进 `dueLater`。而「早上打开看一眼」正是这个产品唯一要占的时刻。
- **本地 08:00–23:59：会虚报。** 一条明早才截止的，此时会被标成今日到期。

方向反了比写错更坏：ADR 是仓库里唯一的持久判据，后来人会拿它当标准去改代码。所以这两条与被推翻的原话一起留在这里。

**新口径的代价**：构建器多了第六个输入。它必须注入而不是在 `ruleOf` 里读 `Date` 的宿主偏移——CI 跑在 `ubuntu-24.04`（TZ=UTC），隐式读会让 required check 钉住的行为和访客浏览器里的不是同一件事，门内绿而线上错。第一版把这写成「那是 `Scope` 的一次扩张」也不成立：加一个可选注入参数不动 `Scope`，真正的理由就是前一句。另外，访客跨时区（出差、换地区）时同一批条目的档位与顺序会变；#9 一旦持久化顺序，它持久化的就是这个口径下的顺序。样例数据也跟着改了口径：`src/fakes/samples.ts` 的截止日按访客本地的当天末尾生成，按 UTC 日造数会在本地下午演示时把「今日到期」演成明天。

**日期形态的截止折算成几点**：T03 把这件事指名交给本票（`tests/today-list.test.ts` 里那句「属 #6 的判定」）。只写日期说的是「这天结束之前」，按午夜折算的话用户在到期日几乎整天看到「已逾期」、今日到期那天永远不出现，所以定在当日 23:59。**未核实的部分**：GitHub `milestone.due_on` 与 Jira `fields.duedate` 到底带不带时刻、带谁的偏移，都还没有一手样本；带时区偏移的日期（`2026-11-18T00:00:00.000+1100`）折算成 UTC 后会落到前一天，这已经足够让日界翻档。真连时先跑 `gh api repos/<有里程碑的仓库>/milestones --jq '.[].due_on'` 与 Atlassian `GET /rest/api/3/issue/<key>?fields=duedate` 再定，改的话改 `toDueInstant` 一处。

**被放弃的选项**：把理由塞成 `Task` 的第八键（破 T03 的七键定稿，且让跨平台合并 T05 先判「这家有没有这个键」）；把逾期判断放进 provider 的 `normalize`（每家各判一次，四家口径分叉，而它需要的 `instant` 在 provider 手里根本没有）；「今日」= 未来 24 小时内（一条明天 00:30 UTC 截止的任务会被今天置顶，而它今天确实来不及——测试 1801/1802 那一对就是为区分这两种口径写的）；用 `score: number` 代替 `reason`（v1 没有任何规则需要打分，加一个从不参与决策的数字是投机字段，且 #8 拿到的解释性更差）；读宿主时区而不注入（上面那条 CI/浏览器分叉）；把 chip 措辞改成「临近截止」来回避日界问题（票面 AC#1 自己用了「今日到期」这个词，措辞层无权把口径改掉）；三档同权重、只靠一行文字承载时间压力（US#23 要的是不读标题就能感知）。

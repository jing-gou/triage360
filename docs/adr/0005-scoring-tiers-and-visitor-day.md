# ADR-0005 · 打分档位由构建器算，"今日" 取访客的日历日

**决策**：顺序由 `buildTodayList` 里的 `ruleOf(task, instant, zoneOffsetMinutes?)` 决定，返回值是三档之一的**理由标识** `reason`（类型 `RuleId`）：`overdue` → `dueToday`（`dueAt` 与 `instant` 落在访客的同一个日历日）→ `noDeadline`（没有 `dueAt`）与 `dueLater`（截止在更晚的那天）；后两个共用一档。前两档怎么比看定稿的第八键 `duePrecision`：带时刻的（`"instant"`）先比瞬间、再比访客日历日；只写日期的（`"day"`）比两个日历日——源站写下的那一天 vs 访客的今天。档位先后写在 `RANK: Record<RuleId, number>` 这一张表里，规则本身不出现数字。档内先按 `updatedAt` 倒序，再按 `id` 的码位序破平。理由跟着**清单条目** `{ task, reason }` 出来，不进 `Task`：第八键装的是源站原值写到哪一层精度，不是打分结论。界面只把标识翻译成词（`REASON_LABELS`），不重算档位；US#23 要的那种「强于普通项」由卡片自己的左边框承担（`styles.css` 的 `.card--overdue` / `.card--dueToday`），不靠把每张卡的理由都加粗。

日界由**注入**的 `zoneOffsetMinutes` 决定：省略即 UTC 日，界面每次构建传 `-new Date().getTimezoneOffset()`。只写日期不带时刻的原始截止值折算成那一天的起点并标 `duePrecision: "day"`，折算与标注只发生在 `dueFrom` 一处。

**原因**：US#27 要的是「规则打分决定顺序、LLM 只负责把理由说成人话」，而置顶的依据是「今天不做就来不及」，不是「刚有人动过」——测试里刻意让逾期项三天没动、干扰项两小时半前才动，按 `updatedAt` 排必然反。分档而不是加权：v1 只有三条规则，一个分数会把 #8「为什么是这几条」需要的可解释性换成一个没人能读的数字，而 #10 学习加权真要加分时 `RANK` 这张表就是它的落点。破平必须靠 `id` 而不是数组位置：provider 返回的顺序不属于本应用，T05 合并四家之后更挡不住——AC#4 那句「同一输入的两次运行一致」只有在这种反例上才可能失败，否则它是一条永远绿的断言。比较用码位序不用 `localeCompare`：id 里带 `:` `#` `/` 与大小写，ICU 给的顺序随宿主变，而今天这批 ASCII 样本还测不出它变了。

**第三档为什么要两个标识**：票面 AC#1 给这一档的词是「其他」。它是个 catch-all——没有截止和截止在十天后进的是同一档，但「最近更新」对后者是句假话，而 AC#2 要的恰恰是原因本身。所以档位不变（`RANK` 里两者同为 2）、标识分开，界面翻译成「无截止时间」与「未到截止日」。

**"今日" 为什么从 UTC 日界改成访客日历日**：本 ADR 第一版把代价写反了，写的是「副作用出现在本地 00:00–08:00：一条今天 UTC 23:59 截止的任务会被说成今日到期，而按本地它已是明天早上」。实测（`TZ=Asia/Shanghai node` 复算 `ruleOf`）：UTC+8 下 `utcDay(dueAt) === utcDay(instant)` 覆盖的本地窗口是本地 D 日 08:00 → D+1 日 07:59，于是

- **本地 00:00–07:59：「今日到期」这一档基本是空的。** 当天中午截止的条目属于下一个 UTC 日，落进 `dueLater`。而「早上打开看一眼」正是这个产品唯一要占的时刻。
- **本地 08:00–23:59：会虚报。** 一条明早才截止的，此时会被标成今日到期。

方向反了比写错更坏：ADR 是仓库里唯一的持久判据，后来人会拿它当标准去改代码。所以这两条与被推翻的原话一起留在这里。

**新口径的代价**：构建器多了第六个输入。它必须注入而不是在 `ruleOf` 里读 `Date` 的宿主偏移——CI 跑在 `ubuntu-24.04`（TZ=UTC），隐式读会让 required check 钉住的行为和访客浏览器里的不是同一件事，门内绿而线上错。第一版把这写成「那是 `Scope` 的一次扩张」也不成立：加一个可选注入参数不动 `Scope`，真正的理由就是前一句。另外，访客跨时区（出差、换地区）时同一批条目的档位与顺序会变；#9 一旦持久化顺序，它持久化的就是这个口径下的顺序。样例数据也跟着改了口径：`src/fakes/samples.ts` 的截止日按访客本地的当天末尾生成，按 UTC 日造数会在本地下午演示时把「今日到期」演成明天。

**标量不是时区：夏令时换日之后每天有一小时算错日号**。`zoneOffsetMinutes` 是访客偏移在**某一个瞬间**的快照，却被用于整轮的**所有**瞬间，所以截止落在换日另一侧的条目会偏一小时。实测（真区取 `America/New_York`，偏移取本地 11-01 00:30 EDT 那一刻的 −240，扫 10-25→11-10）：两周里有 8 个小时日号分叉，正是换日之后每天本地 23:00–23:59 那一段；例如 `dueAt = 2026-11-02T04:30Z`（纽约本地 11-01 23:30 EST）在 `now = 2026-11-01T04:30Z` 下，标量口径给 `dueLater`，按真区逐瞬间取日给 `dueToday`。同一条 `dueAt` 配同一个 `now`，偏移传 −240 与 −300 判出两个档位——档位对这个数字是敏感的，不是理论风险。

不受影响的部分也实测过：非整小时偏移（+05:45、+05:30）与 +13/+14 都算对，因为标量本来就是分钟数。`day` 支躲不开这一小时，只是碰的一侧不同：偏移用来算**访客的今天**（`dayOf(instant, zoneOffsetMinutes)`），写下的那一天按字面取，所以它翻档要等今天自己跨过写下的那天。实测（真 seam，快照 −240 对真 −300，`due_on: "2026-11-01"`、`now = 2026-11-02T04:30Z` 即纽约本地 11-01 23:30）：快照口径 `overdue`，真偏移 `dueToday`；同一条把写下的那天换成 `2026-11-05` 则两侧都 `dueLater`。要修的话退路现成——传 IANA 区名并用 `new Intl.DateTimeFormat("en-CA", { timeZone }).format(...)` 逐瞬间取日（纽约/上海/基里蒂马提/加德满都四区算出的日号都与墙钟一致）。本轮不走：它要把构建器第六个输入从数字换成字符串，换来的只有两支各自午夜边界那一窄条的正确性，而这两窄条其实是同一段钟点——换日之后每天的本地 23:00–23:59。**这条限制记在这里而不是修掉，是因为它一小时只会翻一条边界附近的档位，而换类型的代价落在每一次构建。**

**第 8 键还有一处「同生同灭」没有门**：跨轮状态由调用方保管（ADR-0003），`carryOver` 把上一轮的 `Task` 原样送进打分，不重过 `normalize`。所以 #9 落盘的快照若只存七键，缺 `duePrecision` 的条目会**静默**落回瞬间支：实测（`duedate: "2026-11-17"`、`now` 本地 11-17 09:00、zone `+480`）带键是 `dueToday`，去掉键是 `overdue`——正是这条 ADR 要消灭的那个失效方向。本轮的处理是把它钉在 seam 上（`tests/today-list.test.ts` 「跨轮保留的条目带着第 8 键」，变异验证：`carryOver` 丢键即红），把「快照存全八键」写成调用方的契约；不在 `ruleOf` 里对缺失的键猜一个默认，也不在运行时抛——`duePrecision` 是可选键，`exactOptionalPropertyTypes` 没开，类型层挡不住 JSON 反序列化，挡得住的只有落盘那一步。#9 接线时这一条要跟着进票面。

**只写日期的截止：从「折成 23:59」改口成第 8 键**。T03 把这件事指名交给本票（`tests/today-list.test.ts` 里那句「属 #6 的判定」）。第一版定的是「折成当日 23:59」——理由是只写日期说的是「这天结束之前」，按午夜折算用户在到期日几乎整天看到「已逾期」。这个折算在 UTC 日界下自洽，和本 ADR 同批改掉的「访客日历日」一撞就不成立了：`dueAt` 锚在 **UTC** 那一天的末尾（`2026-11-17T23:59:59Z` = 东八区本地 11-18 早上 07:59:59），档位却按**访客**那一天分，于是同一条在整个 11-17 白天都是 `dueLater`。三条反例都用真 seam 复现过（`buildTodayList` + `jiraLike` 的 `duedate: "2026-11-17"`）：

- zone `+480`、本地 11-17 12:00 → `dueLater`，应为 `dueToday`；
- zone `+480`、本地 11-18 00:30（访客的 11-17 已过完）→ `dueToday`，应为 `overdue`；
- zone `−300`、本地 11-17 19:30（天还没过完）→ `overdue`，应为 `dueToday`。

根因不是那个时刻选得不对，而是**七键把「只写日期」和「恰好某个瞬间」压成了同一个形状**，打分层无从分辨——这句话本来写在 `toDueInstant` 的注释里，当时当成理由，其实是缺陷的自供。任何单一 UTC 时刻都救不了它：+8 要的瞬间和 −5 要的瞬间不是同一个，而「是哪一天」源站已经写死了。所以定稿加第 8 键 `duePrecision`，`day` 走日历日比较（`YYYY-MM-DD` 字典序即时间序），`instant` 维持原样。代价按 2026-11-17 用户确认执行：重开 T03 的七键定稿，改 GLOSSARY 的两条术语、四家 fake provider 的输出与三处形状/期望值断言；`dueAt` 与 `duePrecision` 同生同灭，没有截止时两个键都显式写 `undefined`，键集合照旧恒定。**这条改口把「折成 23:59」连同它的理由一起留在原地**，因为下一次有人想给时间粒度加键时，需要先看到它是怎样在两个口径交汇处失效的。

**仍未核实的部分**：GitHub `milestone.due_on` 与 Jira `fields.duedate` 到底带不带时刻、带谁的偏移，都还没有一手样本——`duePrecision` 现在按「原值有没有那 10 个字符」判，真连样本回来若发现某家把时刻裁掉了，改的是 `dueFrom` 一处。带偏移的日期（`2026-11-18T00:00:00.000+1100`）折算成 UTC 会落到前一天，这在 `instant` 分支里仍会让日界翻档；访客偏移与条目偏移恰好相等时不翻（`2026-11-18T09:00:00.000+0800` + `480` 还是 11-18）。

还有两支不等一手样本就能翻档，先记在这里：① 源站把「哪一天」序列化成**本地午夜的瞬间**（`2026-11-18T00:00:00Z`）时，`DATE_ONLY` 认不出它，于是走瞬间支——实测 `now = 2026-11-18T00:30Z`、zone `−300` 判 `overdue`，而同一天 Jira 写成 `2026-11-18` 走日粒度判 `dueToday`：同一句「11-18 之前做完」，两家差一档。② 脏值（既不是那 10 个字符、也不是可解析时刻）会在 `new Date(raw).toISOString()` 上抛 RangeError 并带走整轮；ADR-0003 认下的「整轮失败」说的是网络，字段级脏值要不要在 `dueFrom` 挡是 #11 真连要定的事。这两条真要收口都改在 `dueFrom` 一处，缺的是「某家实际怎么写」的一手样本，而不是一个新造的判据。

真连时先跑 `gh api repos/<有里程碑的仓库>/milestones --jq '.[].due_on'` 与 Atlassian `GET /rest/api/3/issue/<key>?fields=duedate` 再定。

**被放弃的选项**：把理由塞成 `Task` 的又一个键（定稿装的是跨平台共有的**原值语义**，打分结论是本轮算出来的，进去之后 #9 存的快照会把上一轮的理由冒充成本轮的）；把逾期判断放进 provider 的 `normalize`（每家各判一次，四家口径分叉，而它需要的 `instant` 在 provider 手里根本没有）；「今日」= 未来 24 小时内（一条明天 00:30 UTC 截止的任务会被今天置顶，而它今天确实来不及——测试 1801/1802 那一对就是为区分这两种口径写的）；用 `score: number` 代替 `reason`（v1 没有任何规则需要打分，加一个从不参与决策的数字是投机字段，且 #8 拿到的解释性更差）；读宿主时区而不注入（上面那条 CI/浏览器分叉）；把 chip 措辞改成「临近截止」来回避日界问题（票面 AC#1 自己用了「今日到期」这个词，措辞层无权把口径改掉）；三档同权重、只靠一行文字承载时间压力（US#23 要的是不读标题就能感知）。
关于第 8 键这一改口，当场被否掉的四个替代：承认现状并写进 ADR（等于把「东半球的访客看不到日期型截止的今日到期」登记成语义，而这个产品要占的正是早上那一眼）；把偏移送进 `normalize`（动七法契约签名，四家真连都要接，且同一条卡在不同访客眼里 `dueAt` 不同，#9 的存储与缓存全部跟着变）；靠 `dueAt` 恰好等于某个日首/日尾字面值反推粒度（第一版写的理由是「GitHub 里程碑的真实值就是 `T23:59:59.000Z` 这个形状」——那句话没有一手样本支撑，见上面「仍未核实的部分」，已经撤掉。撤掉之后这个选项照样不成立：带时刻的截止本来就可能落在午夜或日尾，拿字面值当哨兵就是把它们并进日期档）；把「访客日历日」从这条 branch 摘掉（回到本地早上今日档为空的原缺陷）。

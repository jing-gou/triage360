# ADR-0003 · 跨轮状态由调用方注入，"没返回"是跳过、"命中 deletedStates"才是删除

**决策**：seam 1 增加可选输入 `previous`（上一轮清单里的任务）。本轮对「上一轮有、本轮 `search` 不再返回」的 id 发**一次**按 id 批量取回：返回记录的状态命中 `deletedStates()` 才让条目消失，批量里根本没有这个 id 则**保留上一轮那条**（跳过）。取不到的 id 由 provider 从返回数组里**省略**——不是抛错、也不是返回占位记录，因为一次抛错会让一家平台的缺失变成整张清单不见；单条端点上这就是 `status === 404` 那条分支。provider 与构建器都不持久化跨轮状态。

**第二轮与失败态（2026-11-22 由 #16 接上）**：`src/panel/App.tsx` 现在每轮都把上一轮清单交给构建器，触发方式是可见 tab 轮询加手动刷新；一家抛错只让这一家退回上一轮并就地打水印，其余家照常构建（`DECISIONS.md:61` 的「不允许静默空列表」）。真实会话还有一层：服务端 `/api/items` 的活跃视图不返回已关闭条目，所以浏览器把上一轮的 id 作为查询串发给服务端，服务端用同一枚授权按 id 向源站确认，回在 `previous` 里供构建器补取；确认不到（404、请求失败）仍按本决策的「未返回视为跳过」保留原卡。公开演示快照本来就连 `closed` 一起取，第二轮在这里能直接看到卡片消失。至于「404 与请求失败都折叠成数组里没有这个 id」这条边界，其余状态码仍留给 T09 / T15 真连。

**401 / 过期态与换源**：按 Q37「保留上次快照水印」，授权失效的家（含某一档被 401 摘掉）当作本轮失败处理，不把它的旧卡整批删掉——上一轮条目带水印留在原位，角标给「重新连接」；只有从没连过的家才不进构建。水印按 provider 记最后成功时刻，合并卡不会把一侧的失败时刻抄给另一侧。真实会话失效、面板退回公开演示快照时，上一轮清单当场清空：访客自己的卡片不能以「演示数据」的身份继续留在屏上。

**原因**：ticket #5 的 AC#3 两个半句互为反面——「源站已删除的条目在下一轮消失」和「未返回的 id 视为跳过」用的是同一个观察（这条不见了），差别只在**有没有拿到它的状态**。所以「上一轮」必须是可见输入，否则这两句在实现里无法区分，只能二选一：要么把absence 当删除（面板会静默清空），要么根本不刷新（已删除的条目永远挂着）。`docs/PRD.md:102` 的批量语义借自 Super Productivity，它的 `state 未设时保留原完成态` 说的就是同一件事。真实 provider 更不可能自己记上一轮：进程按请求存活，遍历仓库的 Gitee（见 ADR-0004）连"上一次访问过什么"都没有。

**被放弃的选项**：把上一轮塞进 provider 内部状态（seam 1 的输入不再是全部信息来源，假 provider 会变成有状态的测试替身）；构建器直接读库拿快照（把 seam 1 和凭据保管、T13 的存储层绑死）。代价是调用方（现在是界面，之后是后端）要保管上一轮的任务集合——具体存内存还是存快照，留给 T11（#13，存储层）决定。

**T04 之后的一处不对称**：构建器**输出** `ListEntry[]`（`{ task, reason }`），`previous` **收的仍是 `Task[]`**——调用方传清单里的任务。理由是理由属于这一轮：上一轮的 `reason` 跟着条目复活，等于让一轮的打分结果冒充本轮的。合并卡要把 `mergedFrom ?? [task]` 的每个来源都传进来，否则源站关掉其中一侧时，那一侧的 id 不在 `previous` 里，构建器不会去确认，卡片只会少一个跳转而不会消失。#16 票面 AC#6 那句「把上一轮的**清单**作为 `previous` 传给构建器」按本段读：传的是清单里的**任务**（含合并来源）。

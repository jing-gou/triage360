# ADR-0009 · 学习加权插在档位之内，不在档位之间

**决策**：`#10` 的加权是比较函数里的**第二层**，插在档位与更新时间之间：

```text
RANK[reason]  →  learned?.hits 倒序  →  updatedAt 倒序  →  id 码元序
```

它不动 `RANK` 这张表（ADR-0005），也不给条目算一个总分。构建器新增可选注入输入 `orderHistory: readonly PlacementRecord[]`；省略或空数组即「没有学习这回事」，输出回到 ADR-0005 的档内序，`learned` 一个都不出现。记录形状是票面 AC#1 那四个字段加一份当场算下来的分组键：`{ providerId, taskId, group, at, position }`，`position` **0 基**（界面上的「第 1 位」在这里是 `0`）。三个门槛数字住在 `src/core/learning.ts` 一处：窗口 **7 天**、**前三位**以内（`position < 3`）、**两次起**（`MIN_HITS = 2`）。

**为什么插在中间而不是别的位置**：这一票表达的是「同一种紧急度里先看哪条」，不是「这条比逾期还急」。放在 `RANK` 之前会让一个被置顶过两次的无截止项压过逾期项——那是 AC#1 那三档的口径被学习改掉；放在 `updatedAt` 之后则几乎不起作用，档内更新时间的新旧差别通常比两三次置顶的信号更随机，学到的东西会被淹没。放在档位之后、更新时间之前，命中的那条在同档里必然压过没命中的，而 `updatedAt` 与 `id` 照旧管住没命中那些之间的序。seam 测试把这条钉成一条断言（`tests/learning.test.ts`「连续置顶抬不动档位」）。

**分组键从 `url` 派生**（`src/core/source-group.ts`）：定稿的八键里没有 repo 也没有 labels，而平台专有信息不许夹带在八键之外（AGENTS.md），所以 `owner/repo` 只能从 `url` 读出来：`github.com` / `gitee.com` 取 pathname 前两段，其余平台退到 `url.hostname`，`url` 连主机都读不出（相对地址、访客手改过存储）退到 `providerId`。私有化部署的 GitHub Enterprise 因此按整站算，那是口径而不是缺陷——它意味着「你把这家站点的任务连着排前面」这件事仍然被记住，只是粒度粗一档。分组键**存在记录里**而不是回头再算：那条任务下一轮可能已经关掉、转派，从清单上消失了。

**票面「repo / label」里的 label 那一半没做，这是本 ADR 记录的偏离**。`DECISIONS.md:75` 的原句是「按『历史上你反复把某 repo / 某类 label 排到前面』线性加权」，v1 只做 repo。理由不是没时间排：label 进不了这个比较层，因为它要先进 `Task`，而八键在 T03 就定稿了，改键集合不属于 `#10` 的射程；四家的 label 字段形状也还没有一手样本（真连在 T09 / T15 那两支票上）。所以要做 label，顺序是「真连 → 一手样本 → 定稿加键或另开一条派生通道 → 加权多一层」，不是一支 `#10` 能收的。**这一半目前没有票**（票面上那半句被 v1 的 repo 单独兑现了，剩下的部分需要 owner 决定是改 `DECISIONS.md:75` 还是开一张新票）。

**手动区里的卡不带命中标记**：`applyManualOrder` 对手动区里那些条目一律剥掉 `learned`。界面一次落盘写的是**整份**可见顺序（ADR-0007），所以访客拖过一次之后所有已有卡都在手动区里——这句话实际生效的范围是**他还没排过的那些条目**，也就是刷新后新出现的。卡片上那句「因为你连续把 X 排在前面」（AC#3）与弹窗第二段（「最近七天里你把某个来源的任务往前三位放过两次……越不过逾期的那些」）说的都是这一批。手动区里的卡若也挂这句话，就是把访客那一票记在规则头上。

**存放位置与删除义务**：记录和手动顺序同在浏览器 `localStorage`（键 `triage360:learning-records:v1`，写时只留最近 200 条），按 ADR-0008 定的 A 支——#13 的「撤销 = 物理删除该租户 token 与全部数据」与「30 天未访问自动清除」都不覆盖它。于是票面 AC#4 的后半句（「30 天自动清除覆盖这些记录」）**在 v1 的形态下不成立**，它是 #13 落地时要一起改的票面，不是本支能兑现的；AC#5（「清除数据后加权消失，不留隐式记忆」）在本支只钉到 seam 1 能钉的地方：空 `orderHistory` ⇒ 规则序、无命中。真正的「清除」这个动作没有入口——自陈屏归 #13，本支因此不导出 `clearLearningRecords()`：一个没人调的导出会把「有清除入口」这件事写得比实际更满。

**代价**：① 构建器多一个输入，`ListEntry` 多一个可选键，`#8`「为什么是这几条」从此有两个来源层要解释（`reason` 与 `learned`），界面必须两者都说或都不说，不能只说后者。② 计的是**放置次数**而不是不同条目的个数：访客把同一张卡连着置顶两次算两次——区分它要靠条目身份，而条目身份已经被 ADR-0004 那套稳定性问题绑住。③ 门槛是三个写死的数字，v1 没有任何证据说明 2 次比 3 次好；改它只需要改 `learning.ts` 一处，但改之前得先有观察。④ 一份 7 天窗口内不会被清除的记录会在访客换浏览器时全部失效（ADR-0008 的代价，本支把它扩大到记录本身）。

**被放弃的选项**：给每条算 `score: number`（ADR-0005 已经为同一理由拒过一次：一个没人能读的数字换掉可解释性，而 #8 要的就是可解释）；把 repo 塞成 `Task` 的第九键（八键定稿不因一支票重开）；在 `ruleOf` 里读浏览器存储（与 `manualOrder`、`zoneOffsetMinutes` 同一个理由——构建器自己读宿主，CI 与访客浏览器就会排成两种顺序）；把「清除学习记录」做成界面上的常驻按钮（常态要安静，且删除入口归 #13 的自陈屏）；对 `localStorage` 里的记录不验形状直接 `as PlacementRecord[]`（一条缺 `group` 的记录会让整轮读到 undefined，而那是「数据被清过」以外的假象）。

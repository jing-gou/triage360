# ADR-0006 · 合并判据由调用方注入，合并发生在打分之后

**决策**：seam 1 增加可选注入 `sameEvent(a: Task, b: Task): boolean`（`src/core/today-list.ts`），**省略即不合并**。合并的结果落在**清单条目**这一侧：`ListEntry.mergedFrom` 装这一组的全部来源，`Task` 的八键不动（T03 定稿）。分组在打分排序**之后**走一遍清单：每条先看能不能并进某个已开卡片的**表头**，表头就是这一组排最前的那条，`reason` 是它的档位，`mergedFrom` 按同一套序排列。判定只拿表头比，一组对外由表头代表。

**为什么判据必须注入**：「这两条是不是同一件事」的答案来自标题相似度、链接引用、最近打开时间——那是 #18 要买的语义匹配。把任何一种写法嵌进构建器，都等于替 #18 宣布那件事不需要了；而 #7 的 AC#3 后半句要防的恰恰是**错并**：同名而不同事的两条一旦折成一张，用户就再也看不见其中一条。更难看的错并在下一层——同一条 GitHub issue 上关联的两个 task 常常同词、URL 还互为引用，看着最像重复，其实是一个事件的两条记录，而那正是标题判据最容易点头的形状。没有任何判据时最稳的姿态是不并：清单上多一张重复卡是难看，少一张卡是漏看，而漏看的那一条往往是线上问题。所以默认值是保守的那一侧，演示要展示合并就得自己交判据。

**为什么合并在打分之后**：不是为了排版。排序已经按档位→更新时间→id 走完一遍，于是一组里最紧急的那条天然当表头，`reason` 直接是它的档位——「并卡不把逾期折成今日到期」是排序的副产品，不需要再写一条规则，也不会有第二处口径去解释「两条合并算哪一档」。反过来先合并再打分时，表头只能按最近更新或按到达顺序取，那种写法在这份夹具上会给出错的答案：界面实测，`github:1041`（今日到期）与 `gitee:jing-gou/triage360#313`（无截止）合成一张卡之前，后者一直躺在第三档第 4 张，滚动之外没人会把它和上面那条联系在一起。

**代价**：
- **演示画面靠一张登记表撑着**。`src/fakes/samples.ts` 的 `demoSameEvent` 只登记 `github:1041 ↔ gitee:jing-gou/triage360#313` 这一对；#18 之前，界面上「跨平台整合」的价值就卡在这条登记上。#18 交付时换掉的只是判据，接入点与结果形状都不动。
- **跨轮要传的是全部来源，不是表头**。`previous` 收的是 `Task[]`（ADR-0003），合并之后一张卡背后有好几条记录：调用方若把 `entries.map((entry) => entry.task)` 当作上一轮交回来，非表头那些来源就从轮次记忆里消失了，它们的「本轮没返回」再也分辨不出是删除还是缺席。#16（第二轮接线）与 #13（快照存储）接这一段时要按 `mergedFrom ?? [task]` 取全集；界面现在只在挂载时构建一次，所以这条今天还咬不到人。
- 表头代表整组，所以传递性不成立：判定器说 A~B、B~C 而 A 不~C 时，三条同源会出两张卡。v1 四家各至多一条重复，暂时碰不到；真碰到的时候，改的是这里换成一趟 union-find，不是 `mergedFrom` 的形状。
- `sameEvent` 拿到的是两条 `Task`，构建器不限制它读什么；#6 的 AC#3「打分只用元数据，不读正文」对合并同样成立——判定器要去读正文，越界的是注入方，构建器不背这个。

**被放弃的选项**：把来源集合塞进 `Task` 当第 9 键（八键是跨平台最小形状，来源集合是构建器这一侧的结论，和 `reason` 同一个理由）；在 provider 侧合并（一家 provider 看不见别家的条目，要看见就得把清单交出去，那是第二个 seam）；构建器自带一个「标题完全相同就并」的默认判据（AC#3 立刻翻车，而 #18 要卖的正是比字面相同更准的那一层）。
